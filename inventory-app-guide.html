Tech inventory app: build guide

An Android app (Kotlin + Jetpack Compose) backed by a Spring Boot REST API, for tracking the tech and items you own, with photos. Hosted entirely on free tiers.

How to read this

Each section explains what we're using, why we picked it, and what we gave up by not picking the alternatives. You don't need to memorize it. Read sections 1 to 3 first, then come back to each part when you reach that phase of the build plan (section 17).

1. What we're building

Version 1 scope

  • Add, view, edit, and delete items (name, category, brand, model, serial number, purchase date and price, condition, location, notes)
  • Take photos with the camera or pick them from the gallery; several photos per item, one marked as the primary (thumbnail)
  • Item list with search and category filter
  • Item detail screen with a photo gallery and full-screen viewer
  • Login, so the API isn't open to the whole internet

Not in version 1 (on purpose)

Offline mode, barcode scanning, multiple users or sharing, reports and charts. Each of these is a reasonable v2 feature, but adding them now would roughly double the work before you have anything working end to end.

Why keep v1 small?

The hardest part of a first full-stack project isn't any single feature. It's getting the phone, the API, the database, and file storage all talking to each other. Get one thin slice working through every layer first, then widen it.

2. Architecture

The four pieces

PieceIts jobLives on
Android appEverything the user sees. Takes photos, shows lists and forms, calls the API.Your phone or the emulator
Spring Boot APIThe single gatekeeper. Validates input, enforces login, reads and writes the database, uploads and deletes files.Render (free web service)
PostgresStructured data: items, and records describing each photo (not the photo bytes).Neon (free plan)
Object storageThe actual image files.Cloudflare R2 (free tier)

Three rules this design follows

  1. The app never talks to the database. Only the API does. That way validation and security live in one place, and you can change the database without touching the app.
  2. Images don't go in the database. Databases are good at small, structured rows; large binary blobs bloat backups and slow queries. Object storage is built for files and is far cheaper per gigabyte. Postgres stores a pointer (storage_key) to each file.
  3. Image downloads skip the API. The API hands out a temporary "signed URL" and the phone downloads the image straight from R2. This keeps the free API server from moving megabytes of image data around.

3. How a request flows

Tracing a request end to end is the best way to understand any architecture. Here are the three flows that matter.

A. Creating an item

  1. You fill in the form and tap Save. The Compose screen calls viewModel.onSaveClick().
  2. The ViewModel validates the form, sets isSaving = true, and calls itemRepository.create(item).
  3. The repository calls the Retrofit API: POST /api/items with JSON, plus the login token in the Authorization header.
  4. Spring Security checks the token. The controller turns the JSON into a CreateItemRequest DTO and runs bean validation (@NotBlank and so on).
  5. The service maps the DTO to an Item entity and saves it through the JPA repository. Postgres assigns the timestamps.
  6. The controller returns 201 Created with an ItemResponse. The ViewModel updates state, and the screen navigates to the detail page.

B. Uploading a photo

  1. The camera writes a full-size photo to a temporary file. The app resizes it (about 1600px on the long side), re-encodes it as JPEG, and in doing so drops the EXIF metadata, including GPS location.
  2. The app sends POST /api/items/{id}/photos as multipart/form-data.
  3. The API checks the content type and size, generates a key like items/{itemId}/{photoId}.jpg, and streams the file to R2.
  4. Only after the upload succeeds does it insert a row into photos. It returns the photo record with a signed URL.

C. Viewing a photo

  1. GET /api/items/{id} returns the item with a list of photos, each carrying a signed URL valid for about an hour.
  2. Coil loads each URL directly from R2. R2 checks the signature and expiry, then serves the bytes. The bucket itself stays private.

5. Free hosting

Limits change

The numbers below were checked in October 2026. Free tiers get revised, so re-check each provider's pricing page when you sign up.

ServiceFree limits that matterWhy this one
Render (API)512 MB RAM, a small slice of CPU, 750 instance hours/month. Spins down after 15 minutes with no traffic; waking takes about a minute. Bandwidth allowance on the free Hobby plan is small (5 GB/month).Deploys from Git with a Dockerfile, simplest free option for a Java server. You've deployed there before.
Neon (Postgres)0.5 GB storage and 100 compute-hours per project per month. Compute sleeps after 5 minutes idle and wakes in under a second.Permanent free plan. Render's free Postgres expires after 30 days, so we avoid it.
Cloudflare R2 (photos)10 GB storage, 1 million write operations and 10 million read operations per month, free egress (downloads).Most generous free object storage, S3-compatible, no expiring trial.

Will it fit?

  • Photos: at roughly 300–500 KB each after compression, 10 GB holds well over 20,000 photos.
  • Database: item rows are a few hundred bytes. 0.5 GB is effectively unlimited for a personal inventory.
  • Bandwidth: images come straight from R2 (free egress), so Render only serves small JSON.

The cold-start trade-off

Free hosting is free because it sleeps. The first request after 15 idle minutes waits roughly a minute for Render to start your container, plus Spring Boot's own startup. The app handles this with a longer timeout and a "Waking server…" message (section 7) instead of showing an error.

Alternative: Google Cloud Run's free tier scales to zero too, with shorter cold starts, but requires enabling billing. Paying about $7/month for Render's smallest always-on instance removes the sleep entirely. Start free; upgrade only if the wait annoys you.

6. MVVM explained

MVVM (Model–View–ViewModel) is a way of splitting app code so each piece has one job. Here's what each part means in this app:

View (Compose UI)

Draws the screen from the current state and reports user actions. No API calls, no business logic. If you deleted all the logic, it should still render from fake state.

ViewModel

Holds the screen's state, reacts to user actions, calls repositories, and turns results into UI state. Survives screen rotation. Knows nothing about Compose.

Model (Repository + data)

Where data comes from. The repository hides whether data came from the network, a cache, or (later) a local database.

Why bother?

Each layer can be tested alone, rotation doesn't lose state, and you can swap the data source (e.g. add Room) without touching the UI.

Unidirectional data flow

          state (StateFlow<UiState>)
ViewModel ─────────────────────────────► Screen
    ▲                                       │
    └──────── events (onSave, onSearch) ────┘

State only flows down, events only flow up. The screen never changes its own data; it asks the ViewModel to. This makes bugs much easier to trace: if the screen shows the wrong thing, the bug is in the state; if the state is wrong, the bug is in the ViewModel.

What a request looks like through the layers

ItemListScreen        user types "macbook"
   │ onSearchChange("macbook")
ItemListViewModel     updates query, debounces 300 ms, calls repository
   │ itemRepository.search("macbook")
ItemRepository        calls the API, maps DTOs to domain models, wraps errors
   │ api.getItems(search = "macbook")
InventoryApi          Retrofit → GET /api/items?search=macbook

7. Android layers in code

These are trimmed examples to show the shape of each layer. They aren't copy-paste complete.

API interface (Retrofit)

interface InventoryApi {
    @GET("api/items")
    suspend fun getItems(
        @Query("search") search: String? = null,
        @Query("category") category: String? = null,
        @Query("page") page: Int = 0
    ): PageResponse<ItemSummaryDto>

    @GET("api/items/{id}")
    suspend fun getItem(@Path("id") id: String): ItemDetailDto

    @POST("api/items")
    suspend fun createItem(@Body body: CreateItemRequest): ItemDetailDto

    @Multipart
    @POST("api/items/{id}/photos")
    suspend fun uploadPhoto(
        @Path("id") itemId: String,
        @Part file: MultipartBody.Part
    ): PhotoDto
}

Repository

Converts network DTOs into the app's own models and turns exceptions into a result the ViewModel can handle. The ViewModel never sees an HttpException.

class ItemRepository @Inject constructor(
    private val api: InventoryApi
) {
    suspend fun search(query: String): Result<List<ItemSummary>> =
        runCatching { api.getItems(search = query.ifBlank { null }).content.map { it.toDomain() } }
}
Why map DTOs to domain models?

If the API renames a JSON field, you fix one mapper instead of every screen. It costs a few extra classes; for a small app you could skip it, but it's a good habit to show in a portfolio.

UI state

sealed interface ItemListUiState {
    data object Loading : ItemListUiState
    data object WakingServer : ItemListUiState
    data class Success(val items: List<ItemSummary>, val query: String) : ItemListUiState
    data class Error(val message: String) : ItemListUiState
}

A sealed interface forces the screen's when to handle every case, so the compiler catches a forgotten error state.

ViewModel

@HiltViewModel
class ItemListViewModel @Inject constructor(
    private val repository: ItemRepository
) : ViewModel() {

    private val _uiState = MutableStateFlow<ItemListUiState>(ItemListUiState.Loading)
    val uiState: StateFlow<ItemListUiState> = _uiState.asStateFlow()

    init { load("") }

    fun load(query: String) {
        viewModelScope.launch {
            _uiState.value = ItemListUiState.Loading
            val slowTimer = launch {
                delay(3_000)
                _uiState.value = ItemListUiState.WakingServer
            }
            val result = repository.search(query)
            slowTimer.cancel()
            _uiState.value = result.fold(
                onSuccess = { ItemListUiState.Success(it, query) },
                onFailure = { ItemListUiState.Error("Couldn't load items") }
            )
        }
    }
}

Notice the ViewModel exposes a read-only StateFlow and keeps the mutable one private. Only the ViewModel can change state.

Screen (route + stateless screen)

@Composable
fun ItemListRoute(onItemClick: (String) -> Unit, vm: ItemListViewModel = hiltViewModel()) {
    val state by vm.uiState.collectAsStateWithLifecycle()
    ItemListScreen(state = state, onRetry = { vm.load("") }, onItemClick = onItemClick)
}

@Composable
fun ItemListScreen(state: ItemListUiState, onRetry: () -> Unit, onItemClick: (String) -> Unit) {
    when (state) {
        ItemListUiState.Loading -> CircularProgressIndicator()
        ItemListUiState.WakingServer -> Text("Waking server… this can take up to a minute")
        is ItemListUiState.Success -> LazyColumn {
            items(state.items, key = { it.id }) { ItemCard(it, onClick = { onItemClick(it.id) }) }
        }
        is ItemListUiState.Error -> ErrorState(state.message, onRetry)
    }
}

The split matters: ItemListScreen takes only plain data and lambdas, so you can preview it and UI-test it with fake state. No Hilt and no network involved.

Dependency injection (Hilt)

@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides @Singleton
    fun okHttp(auth: AuthInterceptor): OkHttpClient = OkHttpClient.Builder()
        .addInterceptor(auth)
        .readTimeout(90, TimeUnit.SECONDS)   // survives a Render cold start
        .build()

    @Provides @Singleton
    fun api(client: OkHttpClient): InventoryApi = Retrofit.Builder()
        .baseUrl(BuildConfig.API_BASE_URL)
        .client(client)
        .addConverterFactory(Json.asConverterFactory("application/json".toMediaType()))
        .build()
        .create(InventoryApi::class.java)
}

Hilt builds these objects once and hands them to whoever asks with @Inject. In tests you replace the module with one that provides a fake API.

8. Photos on the phone

Capturing

val takePicture = rememberLauncherForActivityResult(ActivityResultContracts.TakePicture()) { ok ->
    if (ok) vm.onPhotoCaptured(pendingUri)
}
val pickPhoto = rememberLauncherForActivityResult(ActivityResultContracts.PickVisualMedia()) { uri ->
    uri?.let(vm::onPhotoPicked)
}
  • TakePicture needs a Uri to write to. Create a file in your app's cache directory and expose it with a FileProvider (declared in the manifest).
  • The system camera app does the capturing, so you typically don't need to request the camera permission yourself. If your manifest declares CAMERA, though, Android requires it to be granted before launching the camera intent.

Preparing for upload

  1. Downscale: decode at a reduced size (about 1600px long side). Phone photos are often 3–8 MB; this brings them to a few hundred KB.
  2. Fix rotation: many cameras save the image sideways and record the rotation in EXIF metadata. Read the EXIF orientation (ExifInterface) and rotate the bitmap before re-encoding, or photos will appear sideways.
  3. Re-encode as JPEG at about 85% quality. Re-encoding also drops the original EXIF, including GPS coordinates, which is a privacy win.
  4. Do it off the main thread (withContext(Dispatchers.Default)) or the UI will freeze.

Displaying

AsyncImage(
    model = ImageRequest.Builder(LocalContext.current)
        .data(photo.url)
        .memoryCacheKey(photo.id)   // signed URLs change; the photo id doesn't
        .diskCacheKey(photo.id)
        .crossfade(true)
        .build(),
    contentDescription = item.name,
    contentScale = ContentScale.Crop
)
Signed URLs and caching

Each time you fetch an item, its photos get fresh signed URLs. Coil caches by URL by default, so every fetch would look like a new image and re-download it. Using the photo id as the cache key fixes this.

9. Spring Boot layers

Controller   HTTP in/out: routes, status codes, DTO validation. No business logic.
   │
Service      Business rules and transactions. "Deleting an item deletes its photos."
   │
Repository   Spring Data JPA interfaces. Database access only.
   │
Entity       JPA classes mapped to tables. Never returned directly from controllers.

Why DTOs instead of returning entities?

  • Control: the API shape stays stable even if the table changes.
  • Safety: you never accidentally expose internal fields.
  • Avoids Hibernate surprises: serializing an entity can trigger lazy loading or infinite recursion (item → photos → item → …).

Java records make DTOs one line each:

public record CreateItemRequest(
    @NotBlank @Size(max = 120) String name,
    @NotNull Category category,
    String brand, String model, String serialNumber,
    LocalDate purchaseDate,
    @PositiveOrZero BigDecimal purchasePrice,
    ItemCondition condition, String location, String notes
) {}

Controller

@RestController
@RequestMapping("/api/items")
@RequiredArgsConstructor
public class ItemController {
    private final ItemService itemService;

    @GetMapping
    public Page<ItemSummaryResponse> list(@RequestParam(required = false) String search,
                                         @RequestParam(required = false) Category category,
                                         Pageable pageable) {
        return itemService.search(search, category, pageable);
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public ItemDetailResponse create(@Valid @RequestBody CreateItemRequest req) {
        return itemService.create(req);
    }
}

@RequiredArgsConstructor is from Lombok and generates the constructor. If you'd rather not use Lombok, write the constructor by hand; constructor injection is the point, not Lombok.

Error handling

One @RestControllerAdvice class turns exceptions into consistent JSON errors, so every controller doesn't need its own try/catch. Spring Boot 3 supports the standard ProblemDetail format:

@RestControllerAdvice
public class ApiExceptionHandler {
    @ExceptionHandler(ItemNotFoundException.class)
    public ProblemDetail notFound(ItemNotFoundException ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    }
}

Configuration and secrets

  • Use Spring profiles: application-local.yml (Docker Postgres and MinIO) and application-prod.yml (Neon and R2).
  • Secrets (database password, R2 keys, JWT secret) come from environment variables set in Render's dashboard, never from files committed to Git.
spring:

10. Data model

-- V1__init.sql
CREATE TABLE items (
    id             UUID PRIMARY KEY,
    name           VARCHAR(120) NOT NULL,
    category       VARCHAR(40)  NOT NULL,
    brand          VARCHAR(80),
    model          VARCHAR(80),
    serial_number  VARCHAR(120),
    purchase_date  DATE,
    purchase_price NUMERIC(10,2) CHECK (purchase_price >= 0),
    condition      VARCHAR(20),
    location       VARCHAR(120),
    notes          TEXT,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE photos (
    id           UUID PRIMARY KEY,
    item_id      UUID NOT NULL REFERENCES items(id) ON DELETE CASCADE,
    storage_key  VARCHAR(300) NOT NULL UNIQUE,
    content_type VARCHAR(50)  NOT NULL,
    size_bytes   BIGINT       NOT NULL,
    is_primary   BOOLEAN      NOT NULL DEFAULT false,
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE INDEX idx_photos_item ON photos(item_id);
-- at most one primary photo per item, enforced by the database
CREATE UNIQUE INDEX uq_photos_one_primary ON photos(item_id) WHERE is_primary;

Design decisions

DecisionWhyTrade-off
UUID idsNot guessable (/items/5 invites trying /items/6), and the server can generate the photo id before uploading the file.Bigger than integer ids and less human-friendly in logs. Irrelevant at this scale.
Category as an enum stored as textSimple, type-safe in Java and Kotlin, easy to filter.Adding a category requires a code change and redeploy. A categories table would let you add them in the app; switch if that bothers you.
NUMERIC for priceExact decimal math. Use BigDecimal in Java.Never use double for money: floating point rounds (0.1 + 0.2 ≠ 0.3).
Partial unique index for primary photoThe database guarantees at most one primary per item, even if there's a bug in the code.Setting a new primary must unset the old one first, in the same transaction.
ON DELETE CASCADEDeleting an item removes its photo rows automatically.The files in R2 aren't deleted by the database; the service must delete them (section 12).

Change from the first plan

Earlier we had a separate GET /api/photos/{id}/url endpoint. It's simpler to include signed URLs directly in item responses: one request per screen instead of one per photo. Keep the separate endpoint only if you later need to refresh an expired URL without re-fetching the item.

REST conventions worth following

  • Plural nouns for resources (/items), HTTP verbs for actions; no /createItem.
  • Correct status codes: 201 for create, 204 for delete, 400 for validation errors, 404 for missing, 401 for no or bad token.
  • Paging from day one. Returning "all items" works until it doesn't.

12. Photo storage

A storage interface

public interface PhotoStorage {
    void put(String key, InputStream data, long size, String contentType);
    void delete(String key);
    URI signedGetUrl(String key, Duration ttl);
}

One implementation (S3PhotoStorage) uses the AWS SDK. Because the service depends on the interface, tests can use a fake, and switching providers means writing one new class.

Pointing the S3 SDK at R2 or MinIO

S3Client.builder()
    .endpointOverride(URI.create(props.endpoint()))   // R2: https://<account-id>.r2.cloudflarestorage.com
    .region(Region.of(props.region()))                // R2: "auto"
    .credentialsProvider(StaticCredentialsProvider.create(
        AwsBasicCredentials.create(props.accessKey(), props.secretKey())))
    .forcePathStyle(true)                             // needed for MinIO
    .build();

Signed URLs come from the SDK's S3Presigner, configured the same way.

Upload: what to validate

  • Content type: allow only image/jpeg, image/png, image/webp.
  • Size: enforced by Spring's multipart limits (section 9).
  • Key: generate it on the server (items/{itemId}/{photoId}.jpg). Never use the client's filename as the key; it can contain path tricks or collide.
  • Ownership: check the item exists before uploading.

Ordering, and what happens when something fails

OperationOrderIf step 2 fails
Upload1. Put file in R2 → 2. Insert photo rowAn orphan file in R2. Harmless; costs a little storage.
Delete1. Delete row(s) in a transaction → 2. Delete files from R2An orphan file again. Never the reverse: a row pointing at a missing file is a broken image in the app.

The rule is: prefer orphaned files over broken references. Database transactions can't include R2, so you choose which failure is acceptable. A v2 cleanup job could delete files with no matching row.

Why upload through the API (for now)

ApproachProsCons
Through the API (v1)Simple, one request, the server validates everything before storing.Image bytes pass through your small free server. Fine for one user.
Presigned direct upload (v2)Phone uploads straight to R2; the server never touches the bytes. Scales well.Three steps (request URL → upload → confirm), harder to validate, more client code.

13. Authentication

Once the API is on the internet, anyone who finds the URL could read or delete your inventory. Auth is required even with a single user.

Recommended for v1: single user + JWT

  1. Your username and a BCrypt hash of your password are set as environment variables on Render (never the plain password).
  2. POST /api/auth/login checks the password against the hash and returns a signed JWT that expires (e.g. after 7 days).
  3. The app stores the token in DataStore. An OkHttp interceptor adds Authorization: Bearer <token> to every request.
  4. Spring Security validates the token on every request. A 401 sends the app back to the login screen.

Spring Security's OAuth2 Resource Server starter can validate JWTs signed with a shared secret, which saves you from writing token parsing yourself.

Options compared

OptionEffortWhen to choose
Single user + JWTLowJust you. Recommended start.
Registration + JWT, users table, owner_id on itemsMediumOthers might use it. Every query must filter by owner, or users see each other's items.
Google Sign-In (backend verifies Google's ID token)MediumYou want no passwords at all. Requires Google Cloud console setup.
Never
  • Store passwords in plain text, or commit secrets to Git.
  • Hard-code the JWT secret in source code.
  • Put the token in a URL query string (it ends up in logs).

  • Run docker compose up -d, then start Spring Boot with the local profile.
  • Create the bucket once in the MinIO console at http://localhost:9001.

Deploy (Render)

# Dockerfile (multi-stage: build with JDK, run with smaller JRE)
FROM eclipse-temurin:21-jdk AS build
WORKDIR /app
COPY . .
RUN ./gradlew bootJar --no-daemon

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /app/build/libs/*.jar app.jar
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75"
EXPOSE 8080
CMD ["java", "-jar", "app.jar"]

The JVM flag keeps Java's memory use inside Render's 512 MB limit. Without it, the container can be killed for running out of memory.

18. Common pitfalls

SymptomCauseFix
App can't reach the local APIUsing localhost from the emulator (that's the emulator itself)Use 10.0.2.2; on a physical phone, use your computer's LAN IP
CLEARTEXT communication not permittedAndroid blocks plain HTTPDebug-only network security config for 10.0.2.2
Uploads fail with 413 or a size exceptionSpring's default multipart limit is 1 MBRaise max-file-size and compress on the phone
Photos appear sidewaysEXIF orientation ignoredRotate using ExifInterface before re-encoding
Item list runs dozens of SQL queriesN+1 problem: loading each item's photos separatelyFetch primary photos in one query (join fetch or a dedicated query). Turn on SQL logging locally to spot it
LazyInitializationExceptionAccessing a lazy relation outside a transactionMap to DTOs inside the service's @Transactional method
Deploy crashes on RenderJVM uses more than 512 MB-XX:MaxRAMPercentage=75; avoid unnecessary starters
Neon connection failsMissing SSLAdd sslmode=require to the JDBC URL
Screen state lost on rotationState held in composables with remember instead of the ViewModelKeep screen data in the ViewModel's StateFlow
Secrets in Git historyCommitted application-prod.yml with keysUse environment variables; if it already happened, rotate the keys (deleting the file doesn't remove history)
Images re-download constantlyFresh signed URL each fetchStable cache keys (section 8)

20. Glossary

TermMeaning
DTOData Transfer Object: a plain class describing what goes over the network, separate from database entities.
EntityA JPA class mapped to a database table.
MigrationA versioned script that changes the database schema; Flyway runs them in order.
Object storageStorage for files ("objects") addressed by key, like S3 or R2. No folders, though keys with slashes look like them.
Signed URLA temporary link with a cryptographic signature that grants access to one private file until it expires.
EgressData sent out of a provider to the internet. Often billed; free on R2.
Cold startThe delay when a sleeping server has to start up before answering the first request.
JWTJSON Web Token: a signed token the server issues at login and checks on each request, without storing a session.
BCryptA deliberately slow password-hashing algorithm, so stolen hashes are hard to crack.
StateFlowA Kotlin observable value that always has a current state; Compose re-renders when it changes.
CoroutineKotlin's lightweight way to run asynchronous code (like network calls) without blocking the UI thread.
Dependency injectionObjects receive the things they depend on instead of creating them, which makes swapping in fakes for tests easy.
Unidirectional data flowState flows down to the UI; events flow up to the ViewModel. Never both ways.
N+1 queryRunning one query for a list, then one more per row. Slow; fix with a join or batch query.
TestcontainersA library that starts real Docker containers (Postgres, MinIO) for your tests and throws them away after.
FileProviderAndroid component that safely shares a file from your app with another app (like the camera) via a content:// URI.
